## Findings

### Superseded by v2

These issues are fully replaced by the v2 architecture and are not worth fixing in isolation:

- `src/lib/store.ts` in-memory globals — v2 replaces this with SQLite persistence keyed by account.
- `src/app/page.tsx` computing the dashboard from `data.added` only — v2 persists all transactions locally and applies `added`, `modified`, and `removed` as deltas.
- `src/app/page.tsx` comparing budgets against all-time transactions instead of the current month — v2 replaces the monthly budget model with a rolling burn rate window.

## Suggested Improvements

- Add a persistence layer. SQLite + Drizzle ORM is the planned approach — see `docs/spec.md` v2. Useful models: `accounts`, `transactions`, `sync_cursors`.

- Move budget and trend calculation server-side or into tested shared domain functions. Right now the API fetches raw Plaid data and the client owns financial logic, which makes correctness harder to protect.

- Add focused tests for:
  - `categorizeTransactions`
  - `compareToBudget`
  - `calculateTrends`
  - Edge cases: refunds, income, transfers, multi-month data, modified transactions, removed transactions

- Make budgets configurable instead of hardcoded in `src/lib/budgets.ts`. Addressed as part of the overhead/expense intent work in v4.

- Consider replacing `next/font/google` with a local or system font if builds should work without network access. The production build failed in the sandbox until network access was allowed for Google font fetching.
